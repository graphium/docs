## Overview

Once a playbook is published, Builders can run it immediately on demand, test it safely in dry-run mode before going live, or configure it to run automatically on a schedule. This article covers all three run modes and explains how to read the Runs list and run detail page to understand what the AI did during each execution.

---

## Running and Testing a Playbook

For a published playbook, the editor header contains two buttons next to **Edit**:

- **Test** (flask icon) — Starts a dry-run test that executes all steps but suppresses external actions. Use this to verify your playbook before running it live.
- **Run** (play icon) — Starts a live run immediately. The playbook executes all steps and takes real actions.

> **Note:** The **Test** and **Run** buttons are only available for a published playbook. A playbook in draft mode must be published first — see [Creating and Publishing a Playbook](/graphium/playbooks/creating-and-publishing-a-playbook).

## What Happens in Test Mode

A "Test run started" popup appears when the test run is queued. The run appears at the top of the **Runs** list in the left sidebar with a **Pending** status, then updates to **Running** while it executes.

Test mode executes all steps but suppresses any real-world side effects:

- **External actions are suppressed.** Any step that would send data to a connection or write to an external system instead logs a note such as *"TEST MODE: Would have executed [action name]."*
- **Vault table writes are suppressed.** No records are created or modified.
- **Review checkpoints are skipped.** The run does not pause for approval in test mode.
- The run detail page shows a **"Test Mode — No side effects were executed"** banner in the left sidebar for the duration of the run.
- Test runs appear in the **Runs** list with a **Test** badge (yellow) so they are visually distinct from live runs.

<Frame>
  <img src="/images/graphium/playbooks/test-playbook.png" alt="Test mode run in progress showing the Test Mode banner" />
</Frame>

> **Note:** Test runs still read from your vault tables and connections. Only write actions and external outputs are suppressed.

## What Happens in a Live Run

Clicking **Run** starts a live execution where the playbook performs real actions:

- All steps execute in sequence. The output of each step is passed to the next.
- **External actions are real.** Any step that sends data to a connection, posts to Slack, writes to a Google Sheet, or updates an EMR record does so immediately.
- **Vault table writes happen.** Records are created or modified as instructed.
- **Review checkpoints are active.** If a resource is set to Requires Review, the run pauses and waits for a Builder to review before continuing.
- If a step **fails**, the run stops at that point and all subsequent steps are marked as **Skipped**.
- Live runs appear in the **Runs** list with their trigger type — **Manual**, **Scheduled**, **Record Added**, **Connection Event**, etc.

## Reading the Run History

The **Runs** list in the playbook editor's left sidebar shows all past and in-progress runs for the current playbook. Each run entry shows:

- **Date and time** — When the run started.
- **Status badge** — The current state: **Completed** (green), **Running** or **Pending** (in progress), **Failed** (red), or **Cancelled**.
- **Trigger type** — How the run was started: **Manual** (plain text), **Test** (yellow badge), **Scheduled**, **Record Added**, **Connection Event**, etc.
- **Step progress** — How many steps completed out of the total (for example, *5/5 steps*).
- **Execution time** — How long the run took (for example, *33s*).

## Reading a Run Detail

Click any entry in the Runs list to open its detail as a full page. The detail page shows:

- **← Back to Playbook** — Click to return to the playbook editor.
- A header with the run's trigger type, status, and elapsed time in the left sidebar, along with a **Test Mode** banner if applicable.
- A **numbered step list** in the left sidebar — each step shows a colored status dot: green (completed), blue (currently running), or gray (pending).
- **Per-step detail** in the main panel — each step shows its title, status badge, a **Context** usage bar (how much of the AI's context window this step has used, for example *15.4K of 200K (8%)*), the step's instructions, and the AI's narration of what it did.
- While a step is actively processing, an animated **"⋯"** (three dots) indicator appears beneath it before its narration streams in. Steps that haven't started yet show a **Pending** badge and *"No messages yet for this step."*

If a step **fails**, the run stops at that step and all subsequent steps are marked as **Skipped**. The error message is shown in the failed step's narration.

## Cancelling a Run

To cancel an in-progress run, open the run detail while the run is still executing and click **Cancel Run** in the left sidebar. A confirmation dialog asks *"Are you sure you want to cancel this run?"* — click **Cancel Run** again to confirm. Steps that have already completed are not rolled back.

<Frame>
  <img src="/images/graphium/playbooks/cancel-playbook-run.png" alt="Cancel Run button and confirmation dialog in the run detail page" />
</Frame>

> **Note:** If the run finishes on its own before your cancellation is processed, you'll see a *"Run not found or already in a terminal state"* message — this is expected and means the run completed just ahead of the cancel request.

## Running a Playbook on a Schedule

Scheduled playbooks run automatically at a configured time and frequency — no manual trigger needed.

### Configuring a Schedule

In the playbook editor, click the **trigger card** at the top of the flow canvas, then select **Scheduled** from the **Run when** dropdown in the Trigger Configuration panel. The panel then shows:

- **Frequency** — How often the playbook runs (for example, Daily, Weekly).
- **Time** — The time of day the run should start (for example, 09:00 AM).
- **Time Zone** — The time zone used to evaluate the scheduled time.

Save and publish the playbook to activate the schedule. The first scheduled run fires at the next occurrence of your configured time.

<Frame>
  <img src="/images/graphium/playbooks/schedule-playbook-trigger.png" alt="Scheduled trigger configuration showing Frequency, Time, and Time Zone fields" />
</Frame>

### Scheduled Run Behavior

- Scheduled runs appear in the Runs list with a **Scheduled** trigger type.
- If the playbook is **disabled**, scheduled runs will not fire until the playbook is re-enabled.
- Multiple scheduled playbooks in the same vault can run concurrently without blocking each other.

> 💡 **Tip:** Use test mode to verify your playbook's logic before publishing on a schedule. This prevents a misconfigured playbook from running live on a recurring basis.

## Run Status Reference

| Status | Meaning |
|--------|---------|
| **Pending** | The run is queued and executing |
| **Completed** | All steps finished successfully |
| **Failed** | A step encountered an error and the run stopped |
| **Cancelled** | The run was manually cancelled by a Builder |

## Troubleshooting

| Issue | Likely Cause | What to Do |
|-------|--------------|------------|
| Test and Run buttons are greyed out | The playbook may not be published | Publish the playbook first — the Test and Run buttons are only active for published playbooks |
| Run does not appear in the Runs list | A connection or network issue may have interrupted the request | Refresh the page and check again |
| A step shows as Skipped | A previous step failed and the run stopped | Open the failed step's detail to read the AI narration, then correct the step's instructions or resource access |
| Scheduled playbook is not running | The playbook is disabled, or the schedule is not yet published | Confirm the playbook is enabled and that the scheduled trigger has been saved and published |
| A step appears stuck with no narration | The step is still processing — look for the animated "⋯" indicator beneath it | Wait for the step to finish; long-running steps (e.g. iterating over many records) can take longer |
| "Run not found or already in a terminal state" appears after clicking Cancel Run | The run completed or failed on its own before the cancellation was processed | This is expected — refresh the Runs list to see the run's final status |
